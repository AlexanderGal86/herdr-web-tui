# Решение проблем

## Интерфейс открылся, но нет подключения к Herdr

1. Убедитесь, что Herdr запущен под тем же пользователем, что и bridge.
2. Проверьте путь к сокету. На Linux стандартный путь — `${XDG_CONFIG_HOME:-$HOME/.config}/herdr/herdr.sock`, на Windows — `%APPDATA%\herdr\herdr.sock`.
3. Если используются разные сессии или development-сборка Herdr, задайте `HERDR_SOCKET_PATH` с фактическим путём перед запуском bridge. Не подставляйте путь клиентского терминального сокета вместо API-сокета `herdr.sock`.
4. Посмотрите сообщение в терминале bridge. Требуется терминальный протокол 22; одна только большая версия Herdr не гарантирует совместимость.
5. В Settings → Bridge проверьте, что включён нужный bridge. По умолчанию веб-клиент подключается к тому же серверу, который отдаёт страницу.

Linux:

```bash
ls -l "${XDG_CONFIG_HOME:-$HOME/.config}/herdr/herdr.sock"
```

PowerShell:

```powershell
Test-Path (Join-Path $env:APPDATA 'herdr\herdr.sock')
```

Наличие файла ещё не доказывает, что процесс Herdr отвечает. После запуска bridge его API можно проверить без изменения сессий:

```bash
curl -f http://127.0.0.1:8787/api/capabilities
```

## Порт уже занят

Выберите свободный порт. Linux:

```bash
HOST=127.0.0.1 PORT=8788 bash scripts/run-bridge.sh
```

Windows:

```powershell
.\scripts\start-tui.ps1 -Port 8788
```

Открывайте выбранный порт в браузере. Для SSH-туннеля правый порт должен совпадать с портом bridge на сервере, левый — с адресом, который открываете локально.

## Вместо темы виден старый интерфейс

- Проверьте Settings → Display → Appearance → Herdr TUI. Если этого пункта нет, сервер отдаёт frontend без изменений этого форка.
- Выполните `npm run build:web` и убедитесь, что `--static-dir` указывает на новый `web/dist`.
- При переносе копируйте каталог целиком, включая `index.html`, `assets` и шрифты; затем перезапустите bridge и обновите страницу.
- Настройка темы для `localhost`, `127.0.0.1` и разных портов хранится отдельно.

## Bash сообщает о символах `\r` после переноса с Windows

Предпочитайте `git clone` на Linux копированию Windows-checkout. Чтобы нормализовать только штатный скрипт запуска в скопированной папке:

```bash
sed -i 's/\r$//' scripts/run-bridge.sh
```

## Ошибка при сборке

Проверьте `node --version`, `npm --version`, `rustc --version` и `cargo --version`. Для этого форка используйте Node.js 24.x и Rust stable. Ошибки linker/C compiler обычно означают, что отсутствует системный toolchain. На Linux устанавливайте пакет сборочных инструментов вашего дистрибутива; на Windows — Visual Studio Build Tools с компонентами C++.

Для ограниченной сети нужен доступ к реестрам зависимостей либо заранее настроенные корпоративные зеркала. Не отключайте проверку TLS ради установки.

## Чем отличается `theme-preview.html`

Это демонстрация с вымышленными сессиями. Она работает только через сервер разработки и никогда не управляет вашим Herdr. Для настоящих сессий используйте `/` на порту 8787 или 5173.

## Страница зависла: мост не отвечает, терминалы не переподключаются

Симптомы (наблюдались 2026-10-12): страница по адресу bridge открывается или висит без ответа, установленные WebSocket-соединения от браузера числятся живыми, но данные не передаются, повторное подключение к терминалам возвращает `terminal not found`.

Диагностика:

1. Проверьте, что процесс слушает порт и отвечает локально:

```bash
ss -tlnp | grep 8787
curl -f http://127.0.0.1:8787/api/capabilities
```

2. Проверьте, проходят ли пакеты от клиента. Если TCP-соединения установлены, но трафика нет (tcpdump молчит), завис сам bridge:

```bash
tcpdump -ni <интерфейс> 'tcp port 8787'
```

3. Посмотрите лог bridge (`~/.config/herdr/herdr-web.log`). Признаки зависания — повторяющиеся записи:

```text
websocket heartbeat timed out stream="terminal"
terminal attach connection closed by daemon ... reason=terminal attach ended: terminal ... not found
```

4. Если TCP-хендшейк вообще не завершается (таймаут на SYN), проверьте файрвол: доступ к порту может быть ограничен allow-списком адресов (`iptables -L INPUT -n`).

Восстановление — перезапустить bridge (демон Herdr при этом продолжает работать, открытые вкладки переподключатся сами, но потерянные терминалы придётся запустить заново):

```bash
systemctl restart herdr-web-tui.service   # при запуске через systemd
```

После перезапуска в логе должны появиться `connected to compatible Herdr daemon` и `listening`.

Корневая причина не устранена: после потери терминалов в демоне bridge не восстанавливает поток — heartbeat истекает, а повторный attach завершается ошибкой вместо чистого переподключения. Кандидат на исследование — `bridge/src/web_bridge.rs` (обработка завершения terminal-стрима). Требуется воспроизведение.

## Известные ограничения

Список проверок и известных ошибок исходного проекта приведён в [документации темы](herdr-tui.md). В частности, frontend проверен на Windows, но полный upstream-набор Windows-тестов падает. Linux-запуск этого форка пока не проверялся.
